# Go-TOPS adoption record

This repository adopts [Go-TOPS](https://github.com/Hedronite/go-tops). `go-tops.yaml` is the
authority: a line here that disagrees with it is wrong.

1. **Adoption.** Go-TOPS, the Go testing and quality protocol.
2. **Protocol version.** 0.4.6.
3. **`gotops` and pinned tools.** `gotops` v0.0.0-20261127075618-44c158697801 (pinned in tools/go.mod). Pins: toolchain go1.27.4 and golangci-lint 2.15.0 (go-tops.lock); go-licenses v2.0.1, gotestsum v1.13.0, govulncheck v1.9.0 (tools/go.mod).
4. **Class and thresholds.** `binary-service`: statement coverage floor 75%, CRAP cap 10, `enforce: ratchet`.
5. **Run the gate locally.** `just gate`, or `go tool -modfile=tools/go.mod gotops gate`. The kit's lint pass reads `.go-tops/golangci.yml`, not this repository's own `.golangci.yml`. The gate finds `golangci-lint` in `.go-tops/bin/` or on `PATH`: a repository whose tests walk the module tree keeps the binary outside it, on `PATH`, because a walk reads the files of `.go-tops/bin/` too. Install the pinned release into a directory outside the checkout, as the workflow's install step does.
6. **Baseline and ledgers.** The baseline is `.go-tops/baseline.json`; only `gotops baseline` writes it, never by hand. It records the build it was measured under, and the run with that build is the ledger leg: this repository's is the `ubuntu` leg of `.github/workflows/go-tops.yml`, and CI fails when that leg reports a ratchet outcome of `skip`. The baseline commands run only on the ledger leg's build. A repository with no ledger gets its first one on the pull request that adds this workflow: the `ubuntu` leg runs `gotops baseline --status`, and when no ledger exists on the base or in the tree it writes one with `gotops baseline --init`, uploads it as the `go-tops-baseline` artifact and fails the run until that file is committed unchanged. Once the workflow is on the default branch, run it by hand (`workflow_dispatch`) and pick `init` to write the first ledger with `gotops baseline --init`, or `refresh` to lower entries with `gotops baseline`; the ubuntu leg runs it and uploads the file as the `go-tops-baseline` artifact, which you commit. A refresh only lowers entries. Raising or adding an entry is manual, with `gotops baseline --accept-regression --reason <text> --owner <handle>`: run it locally on the ledger leg's build, which on another platform is a `linux/amd64` Docker container of `golang:1.27.4` with the repository mounted at `/repo`, `GOTOOLCHAIN=local`, and the pinned golangci-lint 2.15.0 on `PATH` (the workflow's install step shows the archive and its SHA-256). Inside the container run `git config --global --add safe.directory /repo` first, because a checkout mounted on Linux can fail git's dubious-ownership check. The run needs network: the hygiene layer reads the vulnerability database. The mutation survivor ledger is `.go-tops/survivors.yaml`, written with `gotops survivors explain` after a gate run and pruned with `gotops survivors expire`; the acknowledgement ledger is `.go-tops/acks.yaml`.
7. **Exemptions in force.** None.
8. **Known deviations.** None.
